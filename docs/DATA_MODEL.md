# Data model

PostgreSQL 16, created by Alembic migrations in `backend/alembic/versions/` (models in
`backend/src/angel_engine/db/models/`). Conventions:

- Primary keys are UUIDv7 (time-ordered, generated by the application so they can be bound into encryption
  associated data before the row is inserted). All timestamps are `timestamptz` in UTC.
- Enumerations are `text` columns with `CHECK` constraints (values listed below).
- **[E]** marks encrypted `bytea` columns: AES-256-GCM with the investigation's data key (or a system key), bound to
  `ae1|table|column|row_id|investigation_id`. Everything else is stored as plaintext.
- **Investigation-scoped** tables carry `investigation_id`, use composite foreign keys `(investigation_id, x_id)` so
  rows can never link across investigations, and are protected by **row-level security**:
  `USING / WITH CHECK (investigation_id = ANY (ae_scope()))`, where `ae_scope()` reads the transaction-local
  setting `ae.inv_ids` that the API sets only after its authorization check. RLS is `FORCE`d, so it also applies to
  the table owner.

## The evidence chain

```
investigation
 └─ sources ─────────────┐   where something was found (URL [E], host, registrable domain, category, reliability)
     └─ evidence_items ◀─┘   immutable observation or quotation (excerpt [E], captured/published time, region)
          ▲  ▲  ▲
          │  │  └─ finding_evidence (stance: supports | contradicts | context; directly_states; quote span)
          │  │        └─ findings  claim + provenance + verification status + confidence (+ status history)
          │  └─ relationship_evidence ── relationships ── entities   (evidence graph)
          └─ timeline_event_evidence ── timeline_events              (timeline)
```

Every finding row renders as **Source → Finding → Evidence → Timestamp → Confidence → Verification Status**.

| Concept | Values | Rules |
|---|---|---|
| Provenance | `observed`, `source_reported`, `analyst_inference`, `ai_hypothesis` | Never changes after insert (trigger). Evidence items can only be `observed` or `source_reported`, so AI output can never become evidence |
| Verification status | `confirmed_by_source`, `corroborated`, `unverified`, `contradicted`, `ai_hypothesis` | Changes only inside the transition service (trigger checks `ae.transition`); `ai_hypothesis` requires AI provenance |
| Confidence | `low`, `moderate`, `high` + stated basis [E] | Must be empty for findings flagged sensitive |
| Stance | `supports`, `contradicts`, `context` | Contradicting links can be dismissed with a reason [E] |

### Investigations

`investigations`: generated display reference `AE-<year>-<000123>` (a label, never an access token), title,
description [E], purpose [E], purpose category, lawful basis, authorization reference [E], jurisdiction, subject
type, restricted mode (`CHECK subject_type <> 'individual' OR restricted_mode`), status, reviewer and review note [E],
per-investigation retention overrides, AI enabled, legal hold + reason [E], label counters for E-/F-/S-/I-numbers,
version (optimistic locking), lifecycle timestamps and `purge_after`.

| Enumeration | Values |
|---|---|
| Status | `draft`, `pending_review`, `active`, `suspended`, `closed`, `archived`, `refused`, `deleted` |
| Subject type | `organization`, `website`, `public_event`, `public_figure_role`, `individual`, `image_provenance`, `other` |
| Purpose category | `journalism`, `fact_checking`, `due_diligence`, `brand_protection`, `cybersecurity`, `academic_research`, `legal_proceedings`, `law_enforcement`, `misinformation_research`, `image_verification`, `other` |
| Lawful basis | `legitimate_interest`, `public_interest_journalism`, `legal_obligation`, `law_enforcement_authorization`, `research_exemption`, `contract`, `consent`, `other` |

## Database-enforced guarantees

| Guarantee | Mechanism |
|---|---|
| Rows never leak across investigations | RLS on every investigation-scoped table + composite foreign keys |
| Evidence is immutable | `trg_evidence_immutable` blocks changes to excerpt, MAC, capture time, source, origin image, provenance |
| Provenance never changes; status changes are audited transitions | `ae_status_guard` on findings, relationships and timeline events |
| Every non-AI finding, every relationship and every timeline event cites evidence | Deferred constraint triggers at commit |
| Edges and events disappear with their last supporting evidence | `trg_relationship_prune`, `trg_timeline_prune` |
| Status histories are append-only | `ae_history_guard` (rows are removed only together with their parent or by the purge) |
| Final reports are locked | `reports_final_guard` (only the investigation purge or a re-encryption job may touch them) |
| The audit log is append-only | `ae_audit_guard`, `ae_no_truncate`; UPDATE/DELETE privileges revoked from the application roles |
| AI output is never evidence | `CHECK (provenance IN ('observed','source_reported'))` on `evidence_items` |
| Individuals are always restricted | `CHECK (subject_type <> 'individual' OR restricted_mode)` |

## Database roles

| Role | Used by | Notes |
|---|---|---|
| `ae_owner` | Migrations | Owns the schema; not used at run time |
| `ae_app` | API | `NOBYPASSRLS`; no UPDATE/DELETE on `audit_log` |
| `ae_worker` | Workers | `NOBYPASSRLS`; same restrictions |
| `ae_maintenance` | Retention purges, scheduled maintenance, key rotation, the content-free AI token-budget sum | `BYPASSRLS`; used only by code paths that never return content to a person |

The administrator data-subject lookup runs as `ae_app` and scopes row-level security to one investigation at a
time while it compares keyed MACs.

## Keys and searchable encryption

Content columns are encrypted, so search works on **keyed tokens**: stemmed terms are mapped to
`HMAC(HKDF(investigation key, "ae/search/v1"), term)` truncated to 64 bits and stored in GIN-indexed `bigint[]`
columns (`search_tokens`, `title_tokens`, `statement_tokens`, `body_tokens`, clue `tokens`). Keyword search is an
exact-term AND match. URL, content and canonical-name MACs are derived from the same key, so de-duplication and the
administrator data-subject lookup work without decrypting anything. When an investigation's key is destroyed, its
content **and** its search indexes become meaningless at once.

Trigram (`pg_trgm`) search is used only on intrinsically public plaintext: host names, registrable domains and the
names of organization-type entities.
